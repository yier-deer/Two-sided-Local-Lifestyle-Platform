# 3 分钟演示逐字稿（定稿版）

原则：现场不现想词。三段式（用户线→商家线→工程线），**每段第一句固定**——开口不卡壳，中间忘了可以看提词。种子账号见 README（admin 13900000000 / 用户 13611110001~3）。任何 Agent 故障都有降级话术，不冷场。

## 镜头 0 · 开口 15 秒（固定）

「这是探店雷达 ScoutBite。主站是 Java 21，前后端分离；Agent 是独立 Python 服务。我演示三条线：推荐必须带证据，评价必须人审，券和订单在并发下不出错。」

## 第一段 · 用户线（约 60 秒）

**固定第一句：「这条推荐，我敢保证每句话都有出处。」**

对 Agent 说：「今晚想在附近吃辣，两个人，人均 100。」

指卡片讲三件事：

1. 「这 3 家都来自检索，不是模型编的——理由后面挂着评论 ID，可以点开对。」
2. 「每家带一个缺点——只说好话的推荐我不信。」
3. 打开 `evals/replay.html` 输入用户 token：「这是刚才那次对话的 trace，Agent 调了哪些工具、拿了什么事实，全程留痕。」

然后抢券下单（可以口播代替实操）：「券是 Redis 原子扣减，200 人抢 100 张，一会工程线给数字。」

**降级卡片（推荐挂了）**：展示检索出的 3 家店——「主站检索还在，Agent 只是生成层挂了，用户照样能逛。」顺手打开 trace 页讲留痕设计。

## 第二段 · 商家线（约 40 秒）

**固定第一句：「这条回复是 Agent 写的，但发布键在商家手里。」」

评价助手（用核销过的订单）：生成草稿 → 改一个字 → 确认发布。

「草稿引用的是订单事实和评价事实——三维评分预设分原样保留，Agent 不许改。没点确认，库里就没有这条评价（ADR-028：跑完 20 条草稿，新增评价 0 条）。」

切商家账号问 Agent：「为什么这周新客涨了？」

指着回答讲结构：「先观察（数字来自 SQL），再假设（带『可能』），再建议——不把发券说成唯一因果。」

**降级卡片（草稿/分析挂了）**：讲事实清单——「Agent 拿到的瘦事实就这几行，它挂了商家自己照着写，流程不依赖模型。」

## 第三段 · 工程线（约 45 秒）

**固定第一句：「200 并发抢 100 张券，一张都不会多——这是压测数字，不是我的自信。」**

打开 README 压测小节（或终端重放）：

- 「成功恰好 100，Redis 余量 0，DB 新增 100 行——三源对上才算过。」
- 「同人 20 并发双击，只成功 1 次——幂等。」
- 关单对账：「不支付的订单超时后，库存、券、订单状态三个资源全部归位——我等的是真实超时，不是造的数据。」

探索开关（可选，20 秒）：同屏对比 `explore=true|false`——「新店 score 从 15.69 掉到 7.84，探索位是请求级开关，想关就关。」

## 收口 15 秒（固定）

「评测报告在 `evals/reports/latest.md`：推荐 30 例全过，草稿 90%——2 例菜品编造我记在失败清单里，没藏。去掉证据步，编造率会上去。这套步骤不是拍脑袋，是测出来的。」

## 翻车预案（背下来）

| 现象 | 怎么办 |
|---|---|
| 模型超时 | 降级店卡 + 打开 trace 页讲留痕 |
| 草稿生成挂 | 讲事实清单，人工照写 |
| 商家分析挂 | 直接 SQL 查数字讲观察层 |
| 券被自己测没了 | README 种子账号表 + seeder 重置（admin123456） |
| 前端样式炸了 | 立刻切 Swagger / `docs/api.http` |
| 订单已评过 | 用第二个种子用户（13611110002） |
