# 探店雷达 ScoutBite · 产品需求文档

Status: 冻结
Updated: 2026-08-18
Audience: 后端 / Agent 岗位简历项目

## 0. 一句话

做一个**可评测**的本地生活双边系统：用户能被推荐到店并完成评价，商家能被分析并采取下一步动作。

对外产品名：**探店雷达 ScoutBite**。仓库文件夹可以仍叫「点评+agent」，口头和简历只说 ScoutBite。

## 1. 简历主线（15 秒版，今天背熟）

我做了一个前后端分离的本地生活平台：Java 21 主站负责店铺、交易、评价和推流；独立的 Python Agent 用 PRED 对比推荐商家、用 CASDG 生成评价草稿并等人确认，商家侧用工具分析经营、评论和公开竞品。传统侧把优惠券超卖、订单超时关单、新店冷启动做成可演示、可量化的问题。

不要说：「我做了一个类似大众点评的系统，还有智能客服。」

## 2. 为什么做这个，而不是再做一个商城

| 商城课设常见形态 | ScoutBite 要留下的约束 |
|---|---|
| 单边买卖 | 用户 + 商家 + 审核可见性 |
| 有商品就能买 | 地理距离、已审核才可见 |
| 随便写评价 | 评价必须绑定已支付订单 |
| 列表按 id 倒序 | 新店保量、爆款降频 |
| 对话框套一层大模型 | 检索后生成 + 证据引用 + 评测集 |

没有这些约束，项目会塌成 CRUD + 聊天框，面试一轮就穿。

## 3. 角色

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| USER | 看已审核店铺、下单、领券、发帖/评价、用用户 Agent | 看未审核店、未支付；已支付未核销就评价、让 Agent 直接下单 |
| MERCHANT | 入驻、上架套餐、回复自己店的评价、用商家 Agent | 改别人的店、看竞品未公开订单、自动改价 |
| ADMIN | 审核店铺（演示用一键通过） | 不做成完整运营中台 |

系统本身也是角色：超时关单、回补库存和券、给新店探索曝光。

## 4. 用户故事（12 条，每条带验收）

### US-01 注册登录
作为用户或商家，我想注册并登录，以便后续操作带身份。
验收：同一手机号不能重复注册；JWT 里带 `role`；无 token 访问写接口返回 401。

### US-02 商家入驻与审核
作为商家，我提交店铺后要等审核，通过后才被用户看到。
验收：状态只能 `draft → pending → approved / rejected`；`approved` 才出现在 nearby / feed / Agent 检索；拒绝后可改资料重回 pending。

### US-03 附近发现
作为用户，我想按自己的位置看到附近店铺和距离。
验收：`GET /api/shops/nearby` 返回 `distanceKm`；未审核店不出现；可按品类过滤。前端地图由 AI 画，接口合同不变。

### US-04 套餐供给
作为商家，我要上架可买套餐，用户能看到价格、库存、销量。
验收：价格用「分」存储；下架后不能下单；销量只在支付成功后增加。

### US-05 领券与下单
作为用户，我可以领一张店铺满减券，并下单购买到店核销的电子套餐券。
验收：SKU 库存为 1 时两人并发只成功一次；同一 `Idempotency-Key` 只产生一单。下单后是 `CREATED`，支付成功变为 `PAID`（已支付未核销），**此时还不能评价**。

### US-06 模拟支付、超时关单、未核销退单、到店核销
作为用户，我可以模拟支付；超时未付自动关单；付了但没去吃可以退单；到店后核销才算吃过。
验收：
- `CREATED` 才能支付或超时关单（`CANCELLED_TIMEOUT`）；已支付不会被超时关单。
- `PAID` 才能退单（`REFUNDED`），回补套餐库存和满减券。
- `PAID` 才能核销（`REDEEMED`）；核销后不可退。
- 展示销量只在核销成功后 +1。
- 演示用核销码或商家一键核销。

### US-07 评价与商家回复
作为用户，我只能对 **已核销且未评价**（`REDEEMED`）的订单发评价；商家回复要带「商家」标。
验收：`order_id` 唯一；对 `CREATED` / `PAID` / `REFUNDED` 发评一律 409；发布成功后订单变为 `REVIEWED`；商家标由服务端根据身份写入。

### US-08 帖子与推流
作为用户，我能看信息流；新店不会永久沉底，爆款不会吃满一屏。
验收：`scene=nearby|hot|new`；探索开关打开时新店出现，关掉后下沉；同一店铺一屏不超过 1 条。

### US-09 用户 Agent · 推荐商家（PRED）
作为用户，我说「今晚附近吃辣」，Agent 给出 3 家对比。
验收：店必须来自检索结果；每家有理由、至少 1 个缺点、评论证据 ID；不编造店名和折扣。

### US-10 用户 Agent · 评价草稿（CASDG）
作为用户，我从已核销未评订单生成评价草稿，确认后才发布。
验收：候选列表只有 `REDEEMED` 单，不含已支付未核销；草稿可改；未确认绝不落库；发布再走 Java 校验并改为 `REVIEWED`。

### US-11 商家 Agent · 三分析
作为商家，我要看经营波动、评论问题和附近公开竞品。
验收：输出分「观察 / 假设 / 建议」；数字能在工具结果里找到；不能读其他店未公开订单。

### US-12 评测与回放
作为作者，我要证明 Agent 不是「我觉得好」。
验收：一条命令跑黄金集；有 B0/B1/B2 对比；每次调用有 trace；故意去掉证据步后分数下降。

## 5. 明确不做（非目标，写进简历「边界」）

1. 真实微信 / 支付宝支付与分账
2. 套餐搭配推荐（信息不足，幻觉重灾区）
3. 即时通讯、关注社交网络
4. 短视频 / 直播
5. 真实营业执照 OCR 与人工审核中台
6. Elasticsearch / Kafka / K8s（简历扩展位，10 天不做）
7. 万能客服、自动改价、自动全网发帖
8. Agent 自动下单、自动发布评价
9. 小程序 / App 双端
10. 把大模型直连数据库

少一条非目标，后面就多一个膨胀点。

## 6. 页面清单（前端要有，实现交给 AI）

你要会对接，不必手写样式。页面存在是为了 3 分钟演示，不是为了作品集。

用户端：登录注册、附近/列表、店铺详情、下单确认、我的订单、评价助手、推荐对话、信息流。
商家端：入驻、套餐与券、订单、回复评论、分析对话。
演示增强：管理员一键审核。

主验收界面仍是 **Swagger / Knife4j + 前端主路径**。前端挂了，用 http 文件也能走完全流程。

## 7. 失败模式 → 功能（今天最重要的设计方法）

| 失败 | 拦截层 |
|---|---|
| 未审核店被推荐 | 检索强制 `status=approved` |
| 模型编造店名 | 先检索后生成，店 ID 必须在候选里 |
| 没到店就发评 | 评价只绑 `REDEEMED`，支付未核销不能评 |
| 吃之前不能退 | `PAID` 可退，`REDEEMED` 不可退 |
| 模型写没点过的菜 | 草稿只能用订单 SKU 或用户原文 |
| 自动乱发评价 | CASDG 的 Gate，人确认才发布 |
| 券被超卖 | Redis 原子扣减 + 对账 |
| 已支付又被关单 | 状态机 CAS |
| 新店没人看到 | 探索配额 |
| 爆款吃满信息流 | 同店去重 + 已读降权 |
| 商家 Agent 假因果 | 观察 / 假设 / 建议 分层 |

步骤不是品味，是事故清单。

## 8. 非功能需求

| 项 | 最低标准 |
|---|---|
| 正确性 | 券压测超卖率 0；关单与支付不花账 |
| Agent | 约束满足、引用可追溯；有基线对比 |
| 时延 | 推荐 p95 可接受（目标 < 8s，以评测报告为准） |
| 安全 | JWT；Agent 无库存写权限；工具白名单 |
| 可讲性 | 合上电脑能画容器图、推荐图、下单图 |

## 9. 3 分钟演示骨架

登录用户 → 附近店带距离 → Agent 推荐 3 家（有缺点和引用）→ 领最后 1 张券（第二人失败）→ 下单支付 → 评价草稿确认发布 → 商家回复带标 → 商家 Agent 解释新客 → 开关探索看新店曝光。

逐字稿见 `docs/demo-script.md`。
